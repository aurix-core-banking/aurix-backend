# Migrações de Banco de Dados (Flyway)

## Visão Geral

As migrações de banco de dados são centralizadas no módulo **`aurix-shared`** e executadas pelo **Flyway** em todos os serviços que dependem dele. A centralização garante que todo o schema seja criado de forma consistente e que novas tabelas sejam adicionadas em um único lugar.

Apesar do agrupamento, cada serviço enxerga apenas o subconjunto de tabelas relevantes para o seu domínio. As migrações usam `pg_advisory_lock`, o que torna a execução concorrente entre múltiplos serviços segura.

## Estrutura dos Diretórios

```
aurix-shared/src/main/resources/
├── db/migration/   # Migrações versionadas (V1__, V2__, ...)
└── db/rollback/    # Scripts de rollback (não executados pelo Flyway)
```

> **Importante:** o diretório `db/rollback/` **não** é um location do Flyway. Os scripts de rollback são mantidos apenas para referência manual (ex.: operações de contingência).

## Configuração

A configuração fica no `application.yml` de cada serviço (bloco `spring.flyway`):

```yaml
spring:
  flyway:
    enabled: true
    validate-on-migrate: true
    validate-migration-naming: true
    locations: classpath:db/migration
    schemas: aurix
```

- `validate-on-migrate: true`: falha o startup se a migração aplicada não corresponder ao checksum do script atual.
- `validate-migration-naming: true`: exige que os scripts sigam o padrão de versão do Flyway (`V{número}__{descricao}.sql`).
- `schemas: aurix`: as migrações criam/alteram objetos no schema `aurix`.

> **Testes:** nos perfis de teste (`application-test.yml`) o Flyway está desabilitado (`spring.flyway.enabled: false`), pois os testes usam H2 com `ddl-auto: create-drop`.

## Migração Inicial (V1)

A `V1__schema_inicial.sql` foi gerada a partir do mapeamento JPA das entidades (Hibernate `SchemaCreator`) de todos os módulos:

- **195** classes `@Entity` / `@MappedSuperclass`;
- **188** tabelas criadas (schema `aurix`), mais entidades legadas sem `@Table(schema=...)` no schema `public`;
- **99** constraints `FOREIGN KEY` e **2** índices;
- Tabelas com o mesmo nome físico em módulos diferentes foram **unificadas** por união de colunas (ex.: `clientes` do `aurix-shared` + `svc-customer`; `liquidez` do `settlement` + `svc-cambio`).

## Criando uma Nova Migração

1. Crie `V{n+1}__descricao.sql` em `aurix-shared/src/main/resources/db/migration/`.
2. O nome deve conter apenas letras, números e underscores (`validate-migration-naming`).
3. Nunca altere uma migração já aplicada. Crie sempre uma nova versão.
4. Opcional: crie o script de rollback correspondente em `db/rollback/V{n+1}__descricao_rollback.sql`.

## Regras

- Todas as tabelas novas devem ser criadas no schema `aurix` (`CREATE TABLE aurix.tabela (...)`).
- `id` serial/bigserial com `generated by default as identity`.
- Colunas de auditoria: `data_criacao` (NOT NULL), `data_atualizacao`, `versao` (para otimismo), `tenant_id`.
- FK sempre com `ON DELETE` explícito quando houver semântica de cascata.
- Texto livre com limite de tamanho (`VARCHAR(n)`) — use `jsonb` apenas para estruturas dinâmicas.

## Validação no Startup

Cada serviço valida a migração no startup: se o checksum do `flyway_schema_history` não bater com o script, a aplicação falha com `Validate failed`. Isso impede que alterações silenciosas em scripts já aplicados quebrem ambientes de produção.

## Referência de Regeneração do Schema

O DDL foi gerado via `hibernate.cfg` com `hibernate.hbm2ddl.schema_gen`, usando o Hibernate 7.4.1.Final e o driver JDBC do PostgreSQL. Para regenerar, carregue as classes anotadas de cada módulo (`aurix-shared` + módulo) em uma `Metadata` e execute `SchemaCreatorImpl.generateCreationCommands(metadata, true)`.
